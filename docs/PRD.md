## 1. 프로젝트 목표

CodeBlue는 "예쁜 홈페이지 제작사"가 아니라 **매출과 문의 전환을 설계하는 웹사이트 제작사**라는 포지셔닝을 시장에 각인시키는 것을 목표로 한다.

이번 프로젝트(자사 공식 웹사이트)는 다음 세 가지를 동시에 달성해야 한다.

1. **레퍼런스 자체가 세일즈 도구가 된다.** 잠재 고객이 CodeBlue 웹사이트에 접속했을 때 "이 정도 퀄리티와 완성도라면 내 사업도 맡길 수 있겠다"는 확신을 만든다.
2. **전환 설계의 실제 사례가 된다.** 방문 → 신뢰 형성 → 가치 인지 → 문의 전환이라는 심리 흐름을 자사 사이트에서 직접 증명한다.
3. **기술적 신뢰도를 증명한다.** 속도(Core Web Vitals), SEO, 인터랙션 완성도(Apple/Stripe/Linear/Vercel 수준)를 통해 "이 회사는 실력이 있다"는 것을 암묵적으로 증명한다.

즉 이 웹사이트는 **CodeBlue의 가장 중요한 영업 자산(Sales Asset No.1)**이다.

## 2. 문제 정의

### 2.1 시장의 문제
- 대부분의 홈페이지 제작사는 "디자인이 예쁜 홈페이지"를 만드는 데 집중하고, 방문자가 실제로 어떤 심리적 경로를 거쳐 문의로 전환되는지는 설계하지 않는다.
- 소상공인, 병원, 제조업, 스타트업 대표들은 "홈페이지는 있는데 문의가 없다"는 동일한 불만을 갖고 있다. 원인은 대부분 다음과 같다.
  - 신뢰 요소(포트폴리오, 후기, 실적)가 부족하거나 배치가 잘못됨
  - CTA(Call To Action)가 불명확하거나 시점이 어긋남
  - 로딩 속도가 느리고 모바일 경험이 나쁨
  - SEO가 전혀 고려되지 않아 검색 유입 자체가 없음
  - 사이트가 회사의 전문성과 신뢰도를 시각적으로 증명하지 못함

### 2.2 CodeBlue가 겪는 문제 (자사 관점)
- 잠재 고객에게 "우리가 왜 다른 제작사와 다른가"를 설명할 언어와 증거가 부족하다.
- 가격/견적 문의 전에 신뢰를 축적할 채널(포트폴리오, 후기, 프로세스 설명)이 구조화되어 있지 않다.
- 향후 콘텐츠(포트폴리오, 후기, FAQ 등)를 비개발 인력이 직접 운영할 수 있는 관리 체계가 없다.

## 3. 타겟 고객

### 3.1 1차 타겟 (웹사이트 제작 의뢰인)
| 세그먼트 | 특징 | 핵심 니즈 |
|---|---|---|
| 소상공인 | 예산 민감, 빠른 결과 원함 | "돈값 하는 홈페이지", 문의/예약 전환 |
| 병원/의원 | 신뢰·전문성이 절대적 기준 | 원장 프로필, 후기, 청결하고 권위 있는 톤 |
| 제조업 | B2B 실적/레퍼런스 중심 | 카탈로그형 정보, 회사 신뢰도, 문의 폼 |
| 스타트업 | 브랜드 임팩트, 투자 유치용 | 세련된 인터랙션, 스토리텔링, 확장성 |
| 기업 대표(의사결정권자) | ROI에 민감, 최종 결재자 | 명확한 성과 지표, 사례, 프로세스 투명성 |

### 3.2 2차 타겟 (기존 홈페이지 불만족 고객)
- "홈페이지는 있지만 문의가 없다"고 느끼는 사업자
- 리뉴얼/리브랜딩을 고려 중인 기존 사업자
- 니즈: 기존 사이트 대비 명확한 개선 효과(Before/After), 데이터 기반 설득

### 3.3 페르소나 요약
- **김대표 (제조업, 48세)**: 홈페이지가 있지만 5년째 그대로. 문의는 전화로만 온다. "우리 회사가 신뢰감 있어 보였으면 좋겠다."
- **박원장 (병원, 41세)**: 신규 개원. 경쟁 병원 대비 차별화된 이미지가 필요. "환자가 예약 버튼을 누르게 만들고 싶다."
- **이대표 (스타트업, 33세)**: 시드 투자 유치 중. "Stripe나 Linear처럼 보이는 사이트가 필요하다."

## 4. 핵심 가치 제안 (Value Proposition)

> **"예쁜 홈페이지가 아니라, 매출을 만드는 홈페이지."**

1. **전환 설계 (Conversion Design)**: 방문자의 심리(Attention → Trust → Value → Action)를 단계별로 설계하여 문의로 이어지는 구조를 만든다.
2. **신뢰 엔지니어링 (Trust Engineering)**: 포트폴리오, 후기, 프로세스 투명성을 통해 "이 회사는 믿을 수 있다"는 확신을 시각·구조적으로 설계한다.
3. **속도와 SEO (Performance & SEO by Default)**: 모든 사이트는 Core Web Vitals 기준을 통과하고 검색엔진에 최적화된 상태로 출고된다.
4. **프리미엄 완성도 (Premium Execution)**: Apple, Stripe, Linear, Vercel 수준의 마이크로 인터랙션과 미니멀 다크 테마로 "이 회사는 실력이 있다"는 것을 암묵적으로 증명한다.

## 5. 브랜드 포지셔닝

### 5.1 포지셔닝 스테이트먼트
> 홈페이지 제작에 지친 사업자들에게, CodeBlue는 예쁘기만 한 사이트가 아니라 **문의와 매출로 이어지는 설계된 웹사이트**를 제공하는 회사다. 왜냐하면 우리는 디자인이 아니라 **사용자 심리와 전환 구조**를 먼저 설계하기 때문이다.

### 5.2 경쟁 구도에서의 위치
- 저가 템플릿 제작 업체 대비: **전략과 심리 설계의 깊이**로 차별화
- 대형 에이전시 대비: **속도, 밀착 소통, 실질적 전환 성과**로 차별화
- 프리랜서 대비: **일관된 완성도, 기술적 신뢰도(성능/SEO), 사후 관리 체계**로 차별화

### 5.3 톤앤매너
- 프리미엄하지만 차갑지 않음 (신뢰감 있는 다크 테마 + 절제된 컬러 포인트)
- 과장된 카피 대신 **근거(데이터, 포트폴리오, 후기)** 중심 커뮤니케이션
- 미니멀하지만 정적이지 않음 — 스크롤 인터랙션과 모션으로 "살아있는" 느낌

## 6. 성공 지표 (KPI)

### 6.1 비즈니스 지표
| 지표 | 목표치 | 측정 방법 |
|---|---|---|
| 문의 전환율 (방문자 대비 Contact 제출) | ≥ 3% | GA4 이벤트 / Supabase 로그 |
| 포트폴리오 페이지 → 문의 전환율 | ≥ 5% | GA4 퍼널 |
| 평균 스크롤 도달 깊이 (Contact 섹션까지) | ≥ 60% | GA4 스크롤 트래킹 |
| 재방문율 | ≥ 15% | GA4 |

### 6.2 기술 지표 (성능/SEO)
| 지표 | 목표치 |
|---|---|
| Lighthouse Performance (Mobile) | ≥ 90 |
| Lighthouse SEO | 100 |
| LCP (Largest Contentful Paint) | ≤ 2.0s |
| INP (Interaction to Next Paint) | ≤ 200ms |
| CLS (Cumulative Layout Shift) | ≤ 0.1 |
| 검색 노출 핵심 키워드 상위 10위 진입 | 3개월 내 3개 키워드 |

### 6.3 브랜드 지표
- 문의 시 "사이트 보고 신뢰가 갔다"는 언급 비율 정성 추적
- 신규 문의 고객 중 포트폴리오/후기 페이지 열람 비율

### 6.4 이벤트 트래킹 계획 (GA4, ★ 리뷰 반영 신설)
기존 KPI 표는 "GA4로 측정한다"고만 되어 있어 실제로 어떤 이벤트를 언제 발생시킬지가 정의되어 있지 않았다 — 즉 측정 가능성이 없는 목표였다. 아래 이벤트를 최소 셋으로 정의하고, DEVELOPMENT_PLAN.md Phase 13(SEO)에서 함께 구현한다.

| 이벤트명 | 발생 시점 | 주요 파라미터 | 연동 KPI |
|---|---|---|---|
| `cta_click` | 모든 CTA 버튼 클릭 시 | `cta_slot`(hero-primary 등), `page_path` | CTA 위치별 클릭률 |
| `contact_submit` | 문의 폼 제출 성공 시 | `industry`, `source` | 문의 전환율 (6.1) |
| `portfolio_view` | `/portfolio/[slug]` 진입 시 | `portfolio_slug`, `category` | 포트폴리오→문의 전환율 (6.1) |
| `scroll_depth_75` | 페이지 스크롤 75% 도달 시 | `page_path` | 평균 스크롤 도달 깊이 (6.1) |
| `faq_expand` | FAQ 아코디언 열람 시 | `faq_question` | 반론 해소 효과 정성 분석 |

- 이벤트는 `lib/analytics/track.ts`와 같은 단일 래퍼 함수를 통해서만 발생시켜, 추후 GA4 외 다른 도구(예: Amplitude)로 교체 시에도 컴포넌트 코드 변경이 없도록 한다 (ARCHITECTURE.md의 데이터 레이어 분리 원칙과 동일한 사상 적용).

### 6.5 콘텐츠 관리 범위의 의도적 한계 (★ 리뷰 반영 — 의사결정 명문화)
DATA_SCHEMA.md는 포트폴리오/후기/FAQ/서비스/CTA/연락처 6개 엔티티만 관리자 편집 대상으로 정의한다. **Hero 헤드라인, Storytelling 문구, Trust 섹션 통계 라벨 등은 이번 범위에서 코드 레벨 콘텐츠로 남기고 관리자 편집 대상에 포함하지 않는다.**
- **이유**: 이 카피들은 브랜드 메시지의 핵심이라 변경 빈도가 낮고, 무분별한 수정 시 브랜드 톤 일관성이 깨질 위험이 크다. 반면 포트폴리오/후기/FAQ 등은 운영 중 지속적으로 늘어나는 "콘텐츠"의 성격이 강해 관리자 편집이 필요하다.
- **향후 확장 시**: 만약 이 결정이 바뀌어 대표가 직접 헤드라인을 수정하고 싶어진다면, `site_copy(key, value)` 형태의 키-값 테이블을 추가하는 것으로 확장 가능하다 (지금 미리 만들지 않는 이유는 불필요한 선제적 확장이기 때문).

## 7. 기능 요구사항 (Functional Requirements)

### 7.1 공개 웹사이트 (Public Site)
- FR-01: 랜딩 홈페이지 (Hero → Storytelling → Trust → Difference → Portfolio → Review → FAQ → Contact → Footer 구조)
- FR-02: 서비스 소개 페이지 (제공 서비스, 프로세스, 가격 정책 방향성)
- FR-03: 포트폴리오 목록/상세 페이지
- FR-04: 고객 후기 목록 (홈에는 요약, 별도 페이지에 전체 목록 가능)
- FR-05: FAQ 페이지 (아코디언 UI)
- FR-06: 문의(Contact) 폼 — 이름/연락처/회사/예산/요청 내용 입력, 제출 시 알림(이메일 또는 관리자 대시보드 적재)
- FR-07: 전역 CTA 컴포넌트 (플로팅 문의 버튼, 섹션별 CTA 배너)
- FR-08: 반응형 네비게이션 (Desktop Header + Mobile Drawer)
- FR-09: 다국어는 1차 범위 제외 (한국어 단일 언어, 구조상 확장 가능하도록 설계)

### 7.2 데이터 요구사항
- FR-10: 포트폴리오, 후기, FAQ, 서비스, CTA 문구, 연락처 정보는 **하드코딩된 데이터 소스 계층**을 통해 관리되며, UI 컴포넌트는 이 데이터를 Props로만 소비한다 (직접 임베드 금지).
- FR-11: 데이터 접근은 반드시 **Repository/Service 함수 인터페이스**를 경유하여, 추후 Supabase 연동 시 컴포넌트 코드 변경 없이 데이터 소스만 교체 가능해야 한다.

### 7.3 관리자 기능 (2차 Phase, 이번 범위 외 — 구조만 대비)
- FR-12 (예정): 관리자 로그인 (Supabase Auth)
- FR-13 (예정): 포트폴리오/후기/FAQ/서비스/CTA/연락처 CRUD
- FR-14 (예정): 문의 접수 내역 조회 및 상태 관리

## 9. 성능 목표

- **LCP ≤ 2.0s** (Mobile 4G 기준)
- **INP ≤ 200ms**
- **CLS ≤ 0.1**
- **TTFB ≤ 0.6s** (Vercel Edge/Node 런타임 기준)
- 3D(Three.js/R3F) 및 GSAP 애니메이션은 **지연 로딩(dynamic import)** 및 **Intersection Observer 기반 활성화**로 초기 로딩 영향 최소화
- 저사양 기기·모바일에서는 3D/고비용 애니메이션을 경량 버전(정적 이미지 또는 CSS 애니메이션)으로 대체 (상세는 ANIMATION_PLAN.md 참조)

## 10. SEO 목표

- 핵심 키워드: "홈페이지 제작", "병원 홈페이지 제작", "제조업 홈페이지 제작", "랜딩페이지 제작", "전환율 높은 홈페이지" 등
- 페이지별 고유 메타데이터(Title/Description) 100% 적용
- Open Graph / Twitter Card 전 페이지 적용
- JSON-LD: Organization, LocalBusiness, Service, FAQPage, BreadcrumbList 적용
- sitemap.xml, robots.txt 자동 생성 (Next.js Metadata API 기반)
- 시맨틱 HTML 및 논리적 Heading 구조(H1 단일, H2/H3 계층) 준수
- 상세 전략은 SEO_PLAN.md 참조

   - 데이터 접근 레이어(Repository)만 교체, UI/컴포넌트 변경 없음
2. **관리자 대시보드**
   - Supabase Auth 기반 로그인
   - 콘텐츠 CRUD, 문의 접수 관리, 간단한 통계(문의 수, 유입 경로)
3. **콘텐츠 확장**
   - 블로그/인사이트 섹션 (SEO 유입 강화 목적)
   - 산업별 랜딩페이지 (병원 전용, 제조업 전용 등 세그먼트 랜딩)
4. **다국어 지원**
   - next-intl 등을 활용한 한/영 다국어 구조 확장 가능성 대비
5. **마케팅 자동화 연동**
   - 문의 폼 → CRM(예: 노션, 슬랙, 이메일 자동화) 웹훅 연동
6. **A/B 테스트 인프라**
   - CTA 문구, 히어로 카피 등에 대한 실험 인프라 (Feature Flag 방식)
