# WIREFRAME — 섹션 구조 및 심리 설계

버전: v1.0

---

## 1. 설계 프레임워크: AIDA 변형 — Attention → Trust → Value → Action

CodeBlue의 모든 페이지는 다음 4단계 심리 흐름을 기준으로 섹션을 배치한다.

| 단계 | 목적 | 방문자의 내적 질문 |
|---|---|---|
| **Attention** | 3초 안에 시선을 붙잡고 "더 볼 가치가 있다"는 인상을 준다 | "이게 뭐지?" |
| **Trust** | "이 회사는 진짜다, 믿을 만하다"는 확신을 만든다 | "이 사람들 실력 있나?" |
| **Value** | "내 문제를 해결해줄 수 있다"는 구체적 가치를 인지시킨다 | "나한테 뭐가 좋은데?" |
| **Action** | 지금 행동해야 할 이유(긴급성/명확성)와 함께 전환을 유도한다 | "그럼 지금 뭘 하면 돼?" |

이 흐름은 홈페이지 전체 스크롤 여정에 걸쳐 반복·중첩된다. 즉 Trust와 Value는 한 번으로 끝나지 않고, Portfolio/Review 등에서 여러 번 재확인(reinforcement)된다.

## 2. Home (`/`) — 섹션 순서 및 목적

### 전체 섹션 순서
```
01. Header (Sticky Navigation)
02. Hero
03. Storytelling (문제 제기 — "왜 홈페이지에 문의가 없을까")
04. Trust (신뢰 지표 — 실적/숫자/로고)
05. Difference (차별점 — 우리가 다른 이유)
06. Services Overview (구체적 제공 서비스 — Value 구체화) ★리뷰 반영 신설
07. Portfolio (증거 — 실제 사례)
08. Review (사회적 증거 — 고객의 말)
09. FAQ (반론 처리 — 마지막 의심 제거)
10. Contact (전환 — 문의 폼)
11. Footer (보조 신뢰 + 재탐색 경로)
```

> **리뷰 반영 노트**: 기존 설계는 Difference(왜 우리인가) 다음 곧바로 Portfolio(사례)로 넘어가, "그래서 구체적으로 무엇을 만들어주는가"에 답하는 구간이 비어 있었다. 병원 운영자가 스크롤하다 제조업 사례만 먼저 보이면 "나와 무관하다"고 이탈할 위험이 있었기 때문에, Services Overview 섹션을 신설하여 이 공백을 메운다.

### 2.1 Header — Attention 진입 전 신뢰 예열
- **목적**: 첫 인상에서부터 "정돈된, 프리미엄" 인상을 준다. 로고/메뉴/CTA 버튼의 정렬만으로도 신뢰의 첫 신호가 된다.
- **구성**: 로고(좌) / 메뉴(중앙 또는 우) / "문의하기" Primary 버튼(우측 고정)
- **심리 근거**: 방문자는 페이지 본문을 읽기 전에 무의식적으로 Header의 정돈도를 스캔하여 "이 사이트가 전문적인가"를 0.05초 안에 판단한다.

### 2.2 Hero — Attention
- **목적**: 핵심 메시지("예쁜 홈페이지가 아니라 매출을 만드는 홈페이지")를 임팩트 있게 전달하고, 스크롤을 유도한다.
- **구성**:
  - 대형 헤드라인 (핵심 가치 제안 1문장)
  - 서브 카피 (구체적 대상 언급: 소상공인/병원/제조업/스타트업)
  - Primary CTA 버튼 ("무료 상담 신청" 또는 "포트폴리오 보기")
  - 배경: Three.js/R3F 기반 미니멀 3D 인터랙션 또는 그래디언트 다크 비주얼
  - Scroll Indicator (스크롤 유도 아이콘/애니메이션)
- **심리 근거**: 방문자는 3초 안에 "이 사이트가 나와 관련 있는가"를 판단한다. 헤드라인은 일반론이 아니라 타겟이 즉시 자신을 발견할 수 있는 언어로 작성한다.
- **CTA 배치 이유**: Hero의 CTA는 전환이 목적이 아니라 **"이 사이트는 행동을 유도하는 사이트"라는 프레임을 처음부터 심는 것**이 목적이다. 실제 전환은 이후 신뢹 축적 이후 Contact 섹션에서 발생하는 경우가 대다수이므로, Hero CTA는 부담 없는 문구("포트폴리오 보기" 등 저관여 행동)를 병행 배치한다.

### 2.3 Storytelling — Attention → Trust 전이
- **목적**: "홈페이지는 있지만 문의가 없다"는 타겟의 실제 고통(Pain Point)을 언어화하여 공감을 형성한다.
- **구성**: 문제 제기 텍스트 블록 + 스크롤 연동 애니메이션(문장이 순차적으로 드러남, GSAP ScrollTrigger)
- **내용 흐름**: (1) 흔한 홈페이지의 실패 패턴 나열 → (2) "그 이유는 디자인이 아니라 설계의 부재" → (3) CodeBlue의 접근 방식 예고
- **심리 근거**: 사람은 해결책보다 자신의 문제가 정확히 언어화될 때 먼저 신뢰를 느낀다("이 회사는 내 상황을 이해하고 있다"). 이는 Trust 단계로 넘어가는 다리 역할을 한다.

### 2.4 Trust — Trust
- **목적**: 숫자와 사실 기반으로 "이 회사는 실체가 있고 실적이 있다"를 증명한다.
- **구성**: 카운트업 애니메이션 통계(예: 프로젝트 수, 평균 문의 전환 개선율, 협업 고객사 수), 로고 클라우드(협업/고객사 로고 — 초기에는 소수라도 배치, 확장 가능 구조)
- **심리 근거**: 사회적 증거(Social Proof)와 권위(Authority)의 조합. 숫자는 카피보다 신뢰도가 높다.

### 2.5 Difference — Trust → Value 전이
- **목적**: "다른 제작사와 무엇이 다른가"를 3~4개의 명확한 축으로 비교 제시.
- **구성**: 카드형 그리드 (예: 전환 설계 / 신뢰 엔지니어링 / 속도·SEO / 프리미엄 완성도), 각 카드에 아이콘 + 짧은 설명
- **심리 근거**: 방문자는 이 시점에서 "왜 CodeBlue인가"에 대한 논리적 근거를 원한다. 감성적 신뢰(Trust) 다음에 이성적 근거(Value)가 와야 설득이 완결된다.

### 2.6 Services Overview — Value 구체화 (★ 리뷰 반영 신설)
- **목적**: Difference 섹션이 "왜 우리인가"라는 추상적 근거를 제시했다면, 이 섹션은 "그래서 구체적으로 무엇을 만들어주는가"를 명확히 하여 방문자가 자신의 상황에 맞는 서비스를 즉시 식별하게 한다.
- **구성**: 서비스 카테고리 카드 그리드(랜딩페이지 제작 / 병원 홈페이지 / 제조업 사이트 / 브랜드 사이트 등, `service.data.ts` 연동), 각 카드에 "자세히 보기" 링크(→ `/services/[slug]`)
- **심리 근거**: Value 단계에서 방문자는 "내가 필요한 것과 정확히 일치하는가"를 확인하고 싶어 한다. 구체적 서비스 카테고리 제시 없이 곧바로 Portfolio(사례)로 넘어가면, 방문자는 자신의 업종과 무관한 사례만 보고 이탈할 수 있다. Services Overview는 바로 다음에 이어지는 Portfolio 사례를 "내 업종과 관련된 것"으로 필터링해 인지하게 만드는 다리 역할을 한다.
- **CTA 배치 이유**: 이 섹션의 CTA는 "전체 서비스 보기"(→ `/services`) 정도의 저관여 링크로 제한한다. 페이지의 주 CTA는 여전히 Contact 하나로 유지한다(본 문서 4장 "1페이지 1주요 CTA 원칙" 준수).

### 2.7 Portfolio (미리보기) — Value 증거
- **목적**: 실제 결과물을 통해 Value를 시각적으로 증명한다.
- **구성**: 3~4개 대표 사례 카드 (썸네일 + 산업군 태그 + 한 줄 성과), "전체 포트폴리오 보기" 링크(→ `/portfolio`)
- **심리 근거**: 말이 아닌 결과물을 보여줌으로써 Value 주장을 증거로 전환. 산업군 태그(병원/제조업 등)를 통해 방문자가 "내 업종 사례가 있다"는 동질감을 느끼게 한다.

### 2.8 Review — Value의 사회적 증거 (Trust 재확인)
- **목적**: 실제 고객의 목소리를 통해 Value 주장의 신뢰도를 재확인시킨다.
- **구성**: 캐러셀 또는 그리드형 후기 카드 (고객명/업종/후기 텍스트/성과 수치 있으면 강조)
- **심리 근거**: 3자 검증(Third-party Validation)은 자사 주장보다 항상 설득력이 높다. Portfolio 직후 배치하여 "결과물 → 그 결과에 대한 타인의 평가"로 신뢰를 이중으로 축적한다.
- **접근성 주의 (★ 리뷰 반영)**: 캐러셀이 자동 재생될 경우 반드시 **가시적인 일시정지/재생 버튼**을 제공한다(WCAG 2.2.2 Pause, Stop, Hide). hover 시 정지되는 방식만으로는 키보드 사용자가 정지시킬 수 없으므로 접근성 위반이다. 상세 구현 기준은 DESIGN_SYSTEM.md 접근성 원칙, ANIMATION_PLAN.md 참조.

### 2.9 FAQ — 반론 처리 (Action 직전 마찰 제거)
- **목적**: 문의 직전 방문자가 갖는 마지막 의심/망설임(가격, 기간, 유지보수, 소통 방식 등)을 해소한다.
- **구성**: 아코디언 UI, 5~8개 핵심 질문
- **심리 근거**: 전환 직전 최대 이탈 지점은 "확신 부족"이다. FAQ는 반론(Objection)을 미리 제거하여 Contact 섹션 진입 시 심리적 저항을 최소화한다.
- **배치 이유**: 반드시 Contact 바로 위에 배치 — 반론 해소 직후 행동 유도가 이어져야 전환율이 극대화된다.

### 2.10 Contact — Action
- **목적**: 실제 전환(문의) 발생 지점.
- **구성**: 좌측(또는 상단) 신뢰 보강 카피 + 연락처 정보 / 우측(또는 하단) 입력 폼(이름, 연락처, 회사/업종, 예산 범위, 요청 내용)
- **심리 근거**: 폼 필드는 최소화(진입 장벽 감소)하되, 신뢰를 재확인시키는 짧은 카피("24시간 내 회신", "무료 상담")를 폼 옆에 병치하여 마지막 망설임을 제거한다.
- **CTA 배치 이유**: 버튼 문구는 "제출"이 아닌 행동 결과를 명시하는 문구("상담 요청하기", "무료로 진단받기") 사용 — 방문자가 얻을 결과를 명확히 하여 클릭 저항을 낮춘다.

### 2.11 Footer — 보조 신뢰 + 재탐색
- **목적**: 이탈하는 방문자에게 마지막 신뢰 신호(사업자 정보, 연락처, SNS)와 재탐색 경로(사이트맵 링크)를 제공한다.
- **구성**: 회사 정보(상호/사업자번호/주소), 빠른 링크(서비스/포트폴리오/후기/FAQ), 연락처, SNS 링크, 저작권
- **심리 근거**: 법적 정보(사업자등록번호 등)의 명시는 "실체가 있는 회사"라는 신뢰 신호로 작동한다.

## 3. 서브페이지 와이어프레임 요약

### 3.1 `/services` — 서비스 소개
```
Header
→ Hero (서비스 전체 개요, "무엇을 만들어 드리나요")
→ 서비스 카테고리 그리드 (랜딩페이지 / 병원 홈페이지 / 제조업 사이트 / 브랜드 사이트 등)
→ 프로세스 설명 (1.상담 → 2.기획/설계 → 3.디자인 → 4.개발 → 5.배포/관리)
→ CTA 블록 ("우리 사업에 맞는 방식이 궁금하다면")
→ Footer
```
- **심리 흐름**: Value(무엇을 제공하는가) → Trust(프로세스의 투명성) → Action

### 3.2 `/services/[slug]` — 서비스 상세
```
Header
→ Breadcrumb (홈 > 서비스 > {서비스명}) ★리뷰 반영 추가
→ 서비스명 + 한 줄 요약
→ 이 서비스가 필요한 대상 (타겟 정의로 공감 형성)
→ 포함 범위 (체크리스트형)
→ 관련 포트폴리오 사례 2~3개 (Value 증거 재사용)
→ CTA 블록
→ Footer
```

### 3.3 `/portfolio` — 포트폴리오 목록
```
Header
→ Hero (짧은 타이틀 + 필터: 전체/병원/제조업/스타트업/소상공인)
→ 카드 그리드 (썸네일, 산업군, 핵심 성과 한 줄)
→ CTA 블록
→ Footer
```

### 3.4 `/portfolio/[slug]` — 포트폴리오 상세
```
Header
→ Breadcrumb (홈 > 포트폴리오 > {프로젝트명}) ★리뷰 반영 추가
→ 프로젝트 타이틀 + 대표 이미지
→ 문제 정의 (Before: 어떤 문제가 있었나)
→ 해결 접근 (What: 무엇을 어떻게 설계했나)
→ 결과 (After: 성과 지표 — 전환율, 문의 수 변화 등)
→ 비주얼 갤러리 (스크린샷/모션 데모)
→ CTA 블록 ("우리도 이런 결과를 원한다면")
→ Footer
```
- **심리 근거**: Before-Problem → Solution → After-Result 구조는 방문자가 자신의 상황(Before)에 이입하게 만들고, Result를 통해 미래(자신의 After)를 상상하게 한다.

### 3.5 `/reviews` — 후기 전체 목록
```
Header
→ Hero (간단 소개)
→ 후기 그리드/필터(업종별)
→ CTA 블록
→ Footer
```

### 3.6 `/faq` — FAQ 전용 페이지
```
Header
→ Hero
→ 카테고리별 아코디언 (가격/기간/프로세스/유지보수/기술 등)
→ CTA 블록 ("찾는 답이 없다면 직접 문의하세요")
→ Footer
```

### 3.7 `/contact` — 문의 전용 페이지
```
Header
→ Hero (짧고 명확한 행동 유도 카피)
→ 문의 폼 (홈과 동일 컴포넌트 재사용)
→ 신뢰 보강 요소 (응답 시간, 연락처, 지도/주소 - 선택)
→ Footer
```

### 3.8 `/about` — 회사 소개
```
Header
→ Hero (미션/비전)
→ Storytelling (창업 배경/철학)
→ 팀/대표 소개
→ 일하는 방식(프로세스) 요약
→ CTA 블록
→ Footer
```

## 4. CTA 배치 총괄 원칙

1. **1페이지 1주요 CTA 원칙**: 각 페이지에는 하나의 명확한 주요 행동(대부분 "문의하기")만 있어야 한다. 보조 CTA(예: "포트폴리오 보기")는 시각적 위계를 낮춰(Secondary Button) 혼란을 방지한다.
2. **반론 해소 직후 배치**: FAQ → Contact 순서처럼, 심리적 저항이 해소된 직후에 항상 행동 유도가 이어져야 한다.
3. **스크롤 30% 이후 플로팅 CTA**: 방문자가 콘텐츠에 관여하기 시작한 시점(이탈보다 관심이 높아진 시점)부터 화면 하단/우측에 고정 CTA 노출.
4. **서브페이지는 반드시 하단에 CTA 블록으로 수렴**: 모든 서브페이지 여정의 종착점은 `/contact` 또는 홈의 Contact 섹션이어야 한다.
5. **CTA 문구는 행동의 결과를 말한다**: "제출하기"가 아니라 "무료로 진단받기", "지금 상담 시작하기" 등 방문자가 얻는 결과를 문구에 담는다.
6. **롱스크롤 보완 (★ 리뷰 반영 추가)**: Portfolio 섹션 직후에도 저관여 보조 CTA(텍스트 링크형, 예: "더 많은 사례가 궁금하다면")를 배치할 수 있다. 단, Primary 버튼이 아닌 텍스트 링크로 시각적 위계를 낮춰 "1페이지 1주요 CTA" 원칙을 훼손하지 않는다. 목적은 전환 강요가 아니라 관심이 높아진 시점에 다음 행동 경로를 자연스럽게 열어두는 것이다.
